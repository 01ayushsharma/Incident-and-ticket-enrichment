# Known Limitations

Written plainly. Everything here is a conscious scope decision or a real
constraint, not a list of things I would have fixed given ten more minutes.

## Verification gaps — read this first

**Docker was not installed on the machine this was built on.** The
`Dockerfile`, `docker-compose.yml` and `.dockerignore` are written carefully
and the CI workflow exercises them, but `docker compose up --build` has not
been run locally by the author. What *has* been verified locally is the same
topology over real sockets: five processes (alarm API, ticketing API, MCP
server over streamable HTTP, copilot backend, GUI) and a real MCP session.

Trace propagation across the MCP hop is covered by
`tests/integration/test_mcp_transport.py`, which binds three real ports and
asserts on the headers the Alarm API actually received - not on a value the
copilot echoed back to itself. That test exists because the claim was made
here before it was true: the MCP client sent no trace with a call and the
server read none, so every tool call started a fresh `trace-mcp-<uuid>` and
the copilot's id never reached the source systems. The id now travels in the
MCP request's `_meta` and is rebound by a server middleware.

If the compose build fails, the most likely causes are the ONNX model
download during `rag-ingest` on a restricted network, or the MCP health
check's assumption that `GET /mcp` returns any HTTP status rather than
refusing the connection.

**`mypy` and `pip-audit` block CI.** Both used to be advisory - `mypy` with
`continue-on-error`, `pip-audit` with a trailing `|| true` that made the
step incapable of failing. The tree is mypy-clean at the settings in
`pyproject.toml` (not `--strict`), so the leniency was decoration rather
than honesty, and decoration is how a check rots unnoticed. To accept a
specific advisory, add `--ignore-vuln <id>` with a reason rather than
disarming the step.

## Persistence

Conversations, drafts, the audit trail (`copilot/state.py`) and the ticket
store (`ticketing_api/store.py`) are in memory and lost on restart.

Consequences: a backend restart orphans any pending draft; audit trails do
not survive; created tickets vanish. The conversation store is LRU-bounded
at 200 conversations with 12 turns each, so it will not grow without limit,
but it is not durable.

Each is one module behind an interface, so substituting Redis or Postgres is
a contained change.

## Retrieval

- **BM25 is rebuilt in memory** from the vector store whenever the index
  changes. Fine for 202 chunks; wrong for a corpus of tens of thousands. A
  real deployment would use a search engine holding both indexes, or
  Chroma's native full-text support.
- **No reranking.** A cross-encoder over the top ~20 candidates would
  measurably improve precision. Omitted because it reintroduces a PyTorch-
  sized dependency for a corpus this small.
- **Chunk-level retrieval without parent expansion.** A retrieved step
  occasionally lacks the surrounding procedure. Heading-path prefixing
  mitigates this but does not remove it.
- **The 0.32 score floor is tuned to this corpus and this embedding model.**
  Change either and it must be re-measured; the measurement is recorded next
  to the constant.
- **Metadata list fields are `|`-joined strings** because Chroma requires
  scalar metadata, so filtering is substring matching. Adequate for
  controlled vocabularies, not for free text.

## Prompt injection

The layered defence reduces how often an attempt lands; it does not
eliminate the class. Pattern matching is defeatable by an attacker who knows
the patterns, and the fence relies on the model respecting a boundary it is
told about.

**The approval gate is the real control.** No retrieved text can create a
ticket, because creation requires a human to approve a specific draft. The
defences above reduce noise and nuisance; the gate bounds the damage. The
code comments say this too rather than implying the regexes are a solution.

## LLM integration

- **The default provider is deterministic**, so out of the box the prose is
  templated. Tool orchestration, retrieval, citations and the draft are all
  fully live; only the narrative is generated by rules.
- **Real providers are verified against mocks, not live endpoints.** The
  OpenAI-compatible, Gemini and Ollama adapters are tested in
  `tests/unit/test_llm_providers.py` against local ASGI mocks returning each
  provider's documented response shape — request body, auth header,
  structured-output wiring and status-code-to-retryability mapping are all
  asserted. What is *not* proven is that the live service accepts the
  request. The Anthropic adapter has no mock test because it goes through
  the SDK rather than raw HTTP.
- **No token budgeting or cost controls.** Evidence is trimmed for context
  economy, but there is no per-conversation spend cap.
- **Free-tier rate limits still degrade the narrative.** Each request makes
  two model calls (plan, then synthesis). Transient failures (429, 5xx,
  network) are retried with exponential backoff that honours `Retry-After`
  (`LLM_MAX_RETRIES`, default 2; waits capped at 10 s). A tokens-per-minute
  limit on a free tier can still outlast the retries during rapid
  back-to-back requests. The response then carries the deterministic
  structured summary and an `llm` degradation notice. Tools, citations,
  similar tickets and the draft are unaffected.
- **No streaming.** Answers arrive whole, so a long tool chain shows a
  spinner for several seconds.

## Orchestration

- **Plans are chosen from seven intents.** A genuinely novel request falls
  back to the closest match rather than composing a new plan. This is the
  cost of deterministic chaining and is deliberate.
- **Tool steps run sequentially.** Several are independent — correlation and
  similar-ticket search do not depend on each other — and could run
  concurrently for perhaps 30% lower latency.
- **Conversation context is passed to the planner but not deeply used.** A
  follow-up like "now raise a ticket for that" works through intent
  detection rather than through genuine coreference resolution.
- **No cancellation.** A long request runs to completion even if the user
  navigates away.

## Source systems

- **The alarm simulator is synthetic**, generated from a seed. The
  distributions are plausible and the injected structures (floods, causal
  pairs, chattering, recurrence) are realistic, but it is not real plant
  data.
- **The dataset is frozen in time** (2026-04-01 to 2026-09-30). Relative
  windows resolve against that horizon, not the wall clock. This is correct
  for reproducibility but means the data does not age.
- **Generated calculations live in memory**, so a calculation id does not
  survive a restart. The `compute_kpi` tool pairs generate and execute for
  this reason.
- **The ticketing mock is not a real ITSM.** No workflow states beyond the
  five, no SLA tracking, no attachments, no notifications.

## Security

- **No authentication on the copilot backend or the GUI.** Both source
  systems require bearer tokens, but the copilot's own API is open. A real
  deployment needs user authentication (SSO), and the audit trail's `actor`
  field would carry a real identity instead of `user`/`copilot`. The GUI's
  user chip is a display label (`COPILOT_OPERATOR_NAME`) and says
  "sign-in not configured" rather than imitating a login.
- **Chat history lives in the browser session.** Reloading the page starts
  empty; the backend keeps conversations (and their drafts and audit trail)
  in memory until restart. There are no shareable links for the same
  reason, so **Share** exports an answer with its sources as Markdown.
- **CORS is `allow_origins=["*"]`** so the containerised GUI can reach the
  backend. Wrong for production.
- **Default tokens are in `.env.example`** and are obviously placeholders.
  There is no secret rotation and no vault integration.
- **No rate limiting** anywhere.

## Testing

- **325 tests at 88% branch coverage**, but coverage is uneven: the source
  systems and RAG are covered heavily, the GUI not at all. Streamlit pages
  are hard to test meaningfully without a browser driver, so the GUI is
  verified by hand. The per-area and per-suite breakdown is generated from
  the coverage data in [coverage-summary.md](coverage-summary.md) rather
  than typed in, because hand-copied counts are how they drifted apart in
  the first place.
- **No LLM test hits a live endpoint**, for the same reason CI has no keys.
  The adapters are covered against mocks of each provider's documented
  response shape; the remaining gap is the network call itself.
- **No load or concurrency testing.** The stores are thread-safe by
  construction but this is not demonstrated under contention. One concrete
  case was found and fixed rather than left to a load test: the MCP
  execution trace used to be a list on the single shared `McpToolClient`,
  which each `/chat` reset and appended to, so two concurrent requests
  corrupted each other's trace. It is now a contextvar, and Starlette's
  one-task-per-request model is the isolation boundary. Shared mutable state
  elsewhere in the backend has not been audited to the same depth.
- **No mutation testing**, so test quality is argued rather than measured.

## Operability

- **Logs go to stdout only.** No shipping, no aggregation, no dashboards.
  The fields are there for an aggregator to consume; nothing consumes them.
- **No metrics endpoint.** Timings are in the logs and the response, but
  there is no Prometheus surface.
- **No tracing backend.** A trace id flows through all six processes and can
  be grepped, but nothing renders it as a span tree.
- **Health checks are shallow.** They confirm a service is up and, for the
  backend, that MCP is connected and the index is populated. They do not
  verify the source systems are returning correct data.

## Scale

Everything here is sized for a demonstration: 28 assets, 5,024 alarms, 272
tickets, 21 documents, 202 chunks. The analytical endpoints hold the full
alarm set in memory and scan it per request. Correlation is O(n × window)
with a binary-searched window, which is fine at this size and would need
reworking at plant scale.
